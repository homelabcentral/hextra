Hextra یک گردش‌کار توسعه بر روی اسکریپت‌های npm خود ارائه می‌کند: یک **Makefile** خودمستند، یک **devcontainer** مبتنی بر Docker Compose با سرور پیش‌نمایش همیشه‌روشن، و **CI محلی** با act.

<!--more-->

## Makefile

برای فهرست کامل و توضیح‌دار، `make help` را اجرا کنید. هدف‌های مهم، بر اساس گردش‌کار:

### توسعه

| هدف              | چه کاری انجام می‌دهد                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `make dev`       | سرور توسعه با خط لوله کامل پوسته (در هر بازسازی `hugo_stats.json` را می‌نویسد)                                 |
| `make serve`     | سرور توسعه بدون خط لوله پوسته — راه‌اندازی سریع‌تر وقتی فقط محتوا ویرایش می‌کنید                               |
| `make stats`     | بازتولید `docs/hugo_stats.json` (فهرست کلاس‌هایی که Tailwind برای حذف استایل‌های بلااستفاده به آن تکیه می‌کند) |
| `make css`       | کامپایل CSS تولید — ابتدا آمار را بازتولید می‌کند، پس همیشه درست است                                           |
| `make css-watch` | کامپایل مجدد CSS هنگام تغییر؛ در کنار `make dev` اجرا کنید                                                     |
| `make skill`     | بازتولید مرجع مهارت در `skills/hextra/` و درج نسخه از `VERSION` در `.claude-plugin/*.json`                     |

### نوشتن محتوا

| هدف                                    | چه کاری انجام می‌دهد                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `make new-blog NAME=my-post`           | ساخت اسکلت یک نوشته وبلاگ (`docs/content/blog/my-post.md`) به‌صورت پیش‌نویس، با تگ‌ها، نشانگر گزیده و فیلدهای کامنت‌شده نویسنده/کاور/سنجاق |
| `make new-doc NAME=guide/my-page`      | ساخت اسکلت یک صفحه مستندات با عنوان و تگ‌ها؛ `weight` برای جای‌گذاری دستی کامنت‌شده می‌ماند                                                |
| `make new-doc-auto NAME=guide/my-page` | مانند `new-doc`، اما `weight` به‌طور خودکار یکی بیشتر از آخرین صفحه بخش تنظیم می‌شود                                                       |
| `make new-page NAME=showcase/thing`    | ساخت اسکلت هر صفحه‌ای زیر `docs/content/` از طریق آرکتایپ پیش‌فرض                                                                          |

### ساخت و پیش‌نمایش

| هدف            | چه کاری انجام می‌دهد                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `make build`   | بیلد کامل تولید در `docs/public` (ابتدا CSS را کامپایل می‌کند)، بدون پیش‌نویس‌ها — همان چیزی که منتشر می‌شود            |
| `make preview` | بیلد تولید **شامل پیش‌نویس‌ها**، ارائه‌شده توسط کانتینر پیش‌نمایش همیشه‌روشن در [localhost:8043](http://localhost:8043) |

### آزمایش

| هدف                               | چه کاری انجام می‌دهد                                                                                                                                |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make verify`                     | همه چیز، به ترتیب — قالب‌بندی و بازتولید، سپس بررسی دوباره، ساخت و اجرای مجموعه آزمون. فرمان پیش از کامیت                                           |
| `make test`                       | ابتدا `fmt-check` و `skill-check`، سپس مجموعه کامل Playwright روی یک ساخت تولید تازه و بدون پیش‌نویس                                                |
| `make test-a11y`                  | فقط آزمون‌های دسترس‌پذیری (WCAG 2.2 AA)                                                                                                             |
| `make test-mobile` / `test-build` | مجموعه‌های منوی موبایل و خروجی بیلد                                                                                                                 |
| `make test-preview`               | بازسازی پیش‌نمایش (شامل پیش‌نویس‌ها)، سپس اجرای مجموعه آزمون روی کانتینر پیش‌نمایش زنده — همان چیزی که آزمودید همان است که 8043 همچنان ارائه می‌کند |
| `make fmt-check`                  | بررسی قالب‌بندی بدون نوشتن چیزی — همان چیزی که CI اجرا می‌کند                                                                                       |
| `make skill-check`                | بررسی به‌روز بودن مرجع مهارت تولیدشده و مانیفست‌های افزونه                                                                                          |
| `make report`                     | ارائه آخرین گزارش HTML پلی‌رایت روی [localhost:9323](http://localhost:9323)                                                                         |

### انتشار

| هدف                        | چه کاری انجام می‌دهد                                               |
| -------------------------- | ------------------------------------------------------------------ |
| `make bump VERSION=0.13.0` | تنظیم `VERSION` و درج دوباره همان شماره در `.claude-plugin/*.json` |

فایل `VERSION` در ریشه مخزن تنها شماره نسخه در کل درخت است و تنها فایلی که ماشه انتشار را می‌کشد: هر push به `main` که آن را تغییر دهد، تگ `v<VERSION>` می‌زند و انتشار گیت‌هاب را می‌سازد. `bump` نوشتن فایل و بازتولید مانیفست‌ها را در یک گام انجام می‌دهد و نسخه بدشکل، نسخه‌ای که همین حالا در فایل است، و نسخه‌ای که تگش وجود دارد را رد می‌کند. فقط فایل‌ها را ویرایش می‌کند — تا وقتی کامیت merge نشود چیزی منتشر نمی‌شود، پس یادداشت‌ها را تا فرصت هست با `npm run changelog` مرور کنید.

### نگهداری

| هدف                                        | چه کاری انجام می‌دهد                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------------- |
| `make fmt`                                 | اجرای Prettier روی قالب‌ها، CSS و JS                                                |
| `make doctor`                              | عیب‌یابی مشکلات زنجیره ابزار (نسخه‌های Hugo/Node، باینری‌های کهنه)                  |
| `make reset`                               | پاک‌سازی و نصب مجدد `node_modules` — تداخل باینری میزبان/devcontainer را رفع می‌کند |
| `make clean` / `clean-stats` / `clean-all` | حذف خروجی بیلد، تغییرات آمار، یا همه چیز                                            |

{{< callout type="info" >}}
زنجیره وابستگی‌ها اصل ماجراست: `make css` به `stats` وابسته است و `make build` به `css`. اسکریپت‌های خام npm از شما می‌خواهند رقص دومرحله‌ای «بازتولید آمار، سپس بیلد CSS» را به خاطر بسپارید ([چرا](https://github.com/homelabcentral/hextra/blob/main/AGENTS.md))؛ Makefile آن را در خود کدگذاری می‌کند.
{{< /callout >}}

یک اسکریپت `npm run watch:css` نیز وجود دارد که برای علاقه‌مندان به npm، معادل `make css-watch` است.

## اسکلت‌سازی محتوا

هدف‌های `new-*` دور `hugo new` پیچیده شده‌اند، بنابراین Front matter از آرکتایپ‌های `docs/archetypes/`‏ (`blog.md`، `docs.md`، `docs-weighted.md`، `default.md`) می‌آید و فایل موجود به جای بازنویسی، رد می‌شود. `NAME` با یا بدون پسوند `.md` کار می‌کند و مسیرهای تودرتو هم مشکلی ندارند (`NAME=guide/deep/page`).

جزئیاتی که دانستن آن‌ها مفید است:

- **نوشته‌های وبلاگ به‌صورت پیش‌نویس آغاز می‌شوند** (`draft: true`): روی `1313` و `8043` قابل مشاهده‌اند و تا زمانی که این پرچم حذف نشود، از `make build` کنار گذاشته می‌شوند.
- **`new-doc-auto` مقدار `weight` را محاسبه می‌کند** با پویش صفحات موجود پوشه مقصد در لحظه ساخت و افزودن یک واحد به بیشترین مقدار. صفحات پیش‌نویس هم‌ردیف شمرده نمی‌شوند و قراردادهای وزن فاصله‌دار (۱۰، ۲۰، ۳۰…) به ۳۱ می‌رسند، نه ۴۰.
- **فقط انگلیسی** — نسخه‌های ترجمه‌شده (`.fa.md`، `.ja.md`، `.zh-cn.md`) به‌صورت دستی در کنار آن کپی می‌شوند و با چیدمان محتوای موجود مطابقت دارند.

## Devcontainer

devcontainer به‌جای یک ایمیج ساده، با **Docker Compose** ‏(`.devcontainer/docker-compose.yml`) و دو سرویس اجرا می‌شود:

- **`dev`** — ایمیج devcontainer مبتنی بر Go که ویرایشگر شما به آن متصل می‌شود، با مخزن سوارشده در `/workspaces/hextra`. قابلیت‌های devcontainer نسخه Hugo Extended (با نسخه ثابت)، Node 24، Docker CLI متصل به دیمن میزبان، act و GitHub CLI را نصب می‌کنند؛ `postCreateCommand` دستور `npm install` را اجرا می‌کند تا کانتینر از اولین باز شدن آماده بیلد باشد. مجموعه‌ای گزیده از افزونه‌های VS Code (Tailwind، Hugo، Prettier، Git Graph، …) از پیش پیکربندی شده است.
- **`preview`** — یک سرور فایل استاتیک بسیار کوچک (~258 kB) به نام (`pierrezemb/gostatic`) که `docs/public` را فقط‌خواندنی ارائه می‌کند، با `Cache-Control: no-store` تا هرگز صفحه کهنه‌ای را عیب‌یابی نکنید. همراه با کانتینر توسعه راه‌اندازی می‌شود و روشن می‌ماند: اجرای مجدد `make build` (یا `make preview`) سایت ارائه‌شده را بدون راه‌اندازی مجدد کانتینر به‌روز می‌کند.

`devcontainer-lock.json` برای نسخه‌های تکرارپذیر ابزارها در مخزن نگه‌داری می‌شود. `.vscode/hextra.code-snippets` هم در کانتینر و هم در یک نسخه معمولی روی میزبان به‌طور خودکار شناسایی می‌شود — [اسنیپت‌های VS Code](vscode-snippets) را ببینید.

یک volume نام‌دار، `node_modules` را درون کانتینر می‌پوشاند، بنابراین کانتینر باینری‌های npm بومی لینوکس خود (مثل `lightningcss`) را نگه می‌دارد و میزبان باینری‌های macOS را — اجرای `npm install` در یک سمت دیگر سمت مقابل را خراب نمی‌کند.

### اعتبارنامه‌ها

Git و API گیت‌هاب از دو مسیر متفاوت احراز هویت می‌کنند، و دانستن این تفاوت وقتی یکی کار می‌کند و دیگری نه، ارزش دارد.

**Push** از SSH استفاده می‌کند. ویرایشگر ssh-agent میزبان را به داخل کانتینر forward می‌کند، بنابراین خود کلید خصوصی هرگز وارد کانتینر نمی‌شود و امضا را agent انجام می‌دهد. `~/.ssh` فقط به یک دلیل به‌صورت فقط‌خواندنی mount می‌شود: یک agent فوروارد‌شده همه کلیدهایش را عرضه می‌کند و گیت‌هاب اولین کلیدی را که به یک حساب نگاشت شود می‌پذیرد، پس `~/.ssh/config` تنها راه تعیین هویتی است که عرضه می‌شود. در macOS آن فایل به `IgnoreUnknown UseKeychain` در یک بلوک `Host *` ابتدایی نیاز دارد، چون `UseKeychain` فقط مخصوص macOS است و OpenSSH لینوکس کل فایل را به‌خاطر آن رد می‌کند.

**API گیت‌هاب** (`gh`) به‌جای آن از یک توکن استفاده می‌کند، چون یک فراخوانی REST را نمی‌توان با ssh-agent امضا کرد. توکن از طریق بلوک `environment` در compose و با نام `GH_TOKEN` وارد می‌شود و از یک متغیر محیطی روی میزبان می‌آید — چیزی روی دیسک نوشته نمی‌شود. دو نکته معمولاً غافلگیرکننده‌اند: ویرایشگر پروفایل شل شما را فقط یک‌بار هنگام راه‌اندازی می‌خواند، بنابراین یک نمونه در حال اجرا هرگز export تازه‌ای را نمی‌بیند؛ و محیط کانتینر در زمان ساخت تثبیت می‌شود، پس تغییر مقدار یعنی بازسازی کانتینر، نه فقط باز کردن دوباره آن.

### پورت‌ها

هر دو پورت به‌طور خودکار به میزبان هدایت می‌شوند (`forwardPorts` در `devcontainer.json`):

| پورت   | سرویس                                        | چه چیزی دریافت می‌کنید                |
| ------ | -------------------------------------------- | ------------------------------------- |
| `1313` | سرور توسعه Hugo ‏(`make dev` / `make serve`) | بیلد توسعه با بارگذاری مجدد زنده      |
| `8043` | کانتینر همیشه‌روشن `preview`                 | آخرین بیلد **تولید** از `docs/public` |

این تفکیک اهمیت دارد: `1313` بازسازی‌های زنده سریع می‌دهد، در حالی که `8043` بیلد تولید را نشان می‌دهد — CSS فشرده‌شده، پاک‌سازی‌شده و بدون استایل‌های بلااستفاده. هر دو شامل پیش‌نویس‌ها هستند (`make preview` گزینه `-D` را می‌فرستد تا نوشته‌های منتشرنشده در قالب تولید بررسی شوند)؛ فقط خروجی `make build` بدون پیش‌نویس است. پیش از انتشار، `8043` را بررسی کنید.

{{< callout type="warning" >}}
`make test` و `make build` مقدار `baseURL` پیکربندی را در `docs/public` جاسازی می‌کنند، بنابراین پس از هر کدام، پیش‌نمایش روی `8043` بیلدی را ارائه می‌کند که URLهای مطلق آن به جای دیگری اشاره می‌کنند. برای بازگرداندن آن، `make preview` را دوباره اجرا کنید — یا از `make test-preview` استفاده کنید که خودِ بیلد پیش‌نمایش را می‌آزماید و `8043` را درست باقی می‌گذارد. درون devcontainer، ‏`test-preview` با نام سرویس compose به کانتینر دسترسی دارد (`http://preview:8043`)؛ در نسخه روی میزبان، با `PREVIEW_TEST_URL=http://localhost:8043` جایگزین کنید.
{{< /callout >}}

## CI محلی با act

گردش‌کارهای GitHub Actions این مخزن را می‌توان با [act](https://nektosact.com) به صورت محلی در Docker اجرا کرد، پس بررسی‌های یک PR را می‌شود پیش از push آزمود. پیش‌فرض‌ها در `.actrc` هستند (ایمیج اجراکننده، معماری amd64 برای Apple Silicon، استفاده دوباره از کانتینر)؛ Makefile فراخوانی‌ها را می‌پیچد:

| هدف              | چه کاری انجام می‌دهد                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make ci-dry`    | اجرای آزمایشی همه گردش‌کارها (`act -n`): گراف کارها را می‌پیماید و هر گام را بدون راه‌اندازی کانتینر چاپ می‌کند — نحو و سیم‌کشی گردش‌کار را در چند ثانیه بررسی می‌کند، بدون دریافت ایمیج        |
| `make ci`        | همه گردش‌کارهایی که با `pull_request` اجرا می‌شوند — دسترس‌پذیری، خروجی بیلد و منوی موبایل — دقیقاً مثل یک PR، هر کار در یک کانتینر                                                             |
| `make ci-a11y`   | گردش‌کار دسترس‌پذیری (`test-accessibility.yml`): ساخت تولید، سپس بررسی‌های WCAG 2.2 AA با axe-core روی همه صفحات انگلیسی                                                                        |
| `make ci-build`  | گردش‌کار خروجی بیلد (`test-build.yml`): ساخت تولید، سپس ادعاهای asciidoc و render-link و search-data                                                                                            |
| `make ci-mobile` | گردش‌کار منوی موبایل (`test-mobile-menu.yml`): ساخت تولید، سپس مجموعه ناوبری موبایل پلی‌رایت                                                                                                    |
| `make ci-pages`  | کار **build** از استقرار Pages (`pages.yml`) — بررسی می‌کند سایت همان‌طور که GitHub Pages می‌سازد ساخته شود. کار deploy کنار گذاشته شده است: به توکن OIDC گیت‌هاب نیاز دارد و محلی اجرا نمی‌شود |

هر هدف پیش از شروع بررسی می‌کند که act نصب باشد (`brew install act`) و Docker در حال اجرا باشد.

{{< callout type="info" >}}
اجرای نخست کند است: act یک ایمیج اجراکننده حدود ۲ گیگابایتی دریافت می‌کند و گردش‌کارها داخل کانتینر کار، Hugo و مرورگرهای پلی‌رایت را دانلود می‌کنند. `.actrc` گزینه `--reuse` را تنظیم می‌کند که کانتینرهای کار را بین اجراها نگه می‌دارد — اجراهای بعدی همه اینها را رد می‌کنند. برای شروع از نو، کانتینرهای `act-*` را حذف کنید.
{{< /callout >}}

گام‌هایی از گردش‌کار که گزارش آزمون بارگذاری می‌کنند (`actions/upload-artifact`) با یک سرور آرتیفکت محلی که خود act راه می‌اندازد صحبت می‌کنند (`--artifact-server-path` در `.actrc`)؛ آرتیفکت‌های بارگذاری‌شده زیر `/tmp/act-artifacts` قرار می‌گیرند.

داخل devcontainer، ابزار خط فرمان act و Docker از پیش نصب شده‌اند (devcontainer features) و سوکت Docker میزبان mount شده است. توجه کنید که در این حالت کانتینرهای کار act به صورت **هم‌نیا** روی دیمن میزبان اجرا می‌شوند، نه تودرتو — پس bind mountها باید روی میزبان قابل حل باشند و اجرای `make ci` از یک checkout روی میزبان مسیر مطمئن است؛ act داخل کانتینر را در حد تلاش حداکثری بدانید.
